Implemented Phase 3 delivery artifact creation after verified paid NewebPay payment intents. The NotifyURL path now reuses the same paid delivery foundation proven by operator fake-paid QA:

```text
verified NewebPay NotifyURL
-> matching payment_intent marked paid

-> pa_ token hash stored at rest
```

## Shared Delivery Service Design
Added `createPaidDeliveryArtifactsForPaymentIntent(...)` in `apps/web/src/lib/payments/paid-delivery-artifacts.ts`.

The service creates/reuses:
- `entitlements`
- hash-at-rest `pa_` paid access token
- paid `generation_jobs`

It preserves:
- idempotency by existing entitlement lookup on `payment_intent_id`
- idempotency by existing paid generation job dedupe behavior
- first-response-only raw token behavior for explicitly controlled operator paths
- no raw token exposure for provider NotifyURL paths

## NotifyURL -> Delivery Artifact Behavior
Phase 2 verification remains the gate:
- invalid signature does not mark paid and does not create artifacts
- malformed payload does not mark paid and does not create artifacts
- amount mismatch does not mark paid and does not create artifacts
- failed/cancelled provider status does not mark paid and does not create artifacts

Verified successful NotifyURL:
- marks matching `newebpay` payment intent paid
- calls the shared delivery service with `entitlementSource: payment_single`
- creates/reuses a paid generation job with `triggerSource: payment_success_future`
- does not trigger queue/processor
- does not send LINE delivery

Duplicate NotifyURL:
- if payment intent is already `paid`, calls the shared delivery service idempotently
- does not duplicate entitlement
- does not duplicate generation job
- returns safe `duplicate_notify`

## pa_ Token Exposure Decision
NotifyURL is server-to-server and does not expose raw `pa_` tokens.

For real NewebPay paid flow in this phase:
- raw `pa_` token is generated by the entitlement helper
- token hash is stored at rest
- raw token is intentionally not returned in NotifyURL result or provider response

Known gap:
- A safe user-facing paid-access link delivery channel is still required before real users can receive the `pa_` unlock URL after NewebPay payment.
- Phase 3 keeps this server-side only rather than inventing an unsafe public lookup.
- Candidate follow-up: Phase 3B/4 ReturnURL/session-bound access handoff or queue/orchestration path that can deliver the paid access route safely.

## generation_job Behavior
- Provider-paid jobs are created with `triggerSource: payment_success_future`.
- Jobs start in the existing queued state used by the paid generation processor.
- No queue trigger is added.
- No automatic processor call is added.
- Existing manual/internal processor compatibility remains unchanged.

## ReturnURL / Status Behavior
ReturnURL remains non-mutating:
- may read/display payment intent status
- does not mark payment paid
- does not verify provider payload
- does not create entitlement
- does not create `pa_` token
- does not create generation job
